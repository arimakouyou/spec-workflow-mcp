# 設計準拠

承認済み design.md からの逸脱を防ぐためのルール。

## 原則

**実装フェーズで承認済みの設計を変更しない。** design.md で定義された DB スキーマ、API 設計、データモデルは実装に対する「契約」であり、実装者が一方的に変更してはならない。

## 実装中の禁止事項

### DB スキーマ
- design.md で定義されていないテーブルやカラムを追加しない
- 既に定義されたカラムの型や制約を変更しない
- 許可なくインデックスを追加・削除しない
- **FK ON DELETE 動作は design.md の定義通りに実装する**（許可なく CASCADE / RESTRICT / SET NULL を変更・追加しない）
- NULL / NOT NULL 定義は design.md に従う

### API
- design.md で定義されていないエンドポイントを追加しない
- 定義済みの HTTP メソッド、パス、ステータスコードを変更しない
- リクエスト/レスポンスフィールドの追加、削除、型変更をしない
- エラーレスポンスのフォーマットを変更しない
- **エラーコード**: design.md の Error Handling セクションで定義されたエラーコードのみを使用する。実装中に未定義のエラーケースが発生した場合、以下の順序で対応する:
  1. design.md で既に定義されているエラーコードで代替できないか検討する（例: `Conflict` が未定義なら `BadRequest("duplicate key")` で代替）
  2. 代替が不可能な場合、ユーザーにエスカレーションして確認する

### データモデル
- design.md で定義されていないフィールドを Model / DTO に追加しない
- DTO と API 定義の間に不一致を生じさせない

## 設計変更が必要な場合

実装中に設計上の問題が発覚した場合:

1. 実装を中断する
2. 問題と提案する変更を明確に記述する
3. ユーザーにエスカレーションする（review-worker の `review_action: escalate`）

ユーザーの判断に基づき、以下のいずれかで進行する:

**判断基準（A vs B の選択指針）:**

| 指標 | A（実装調整） | B（フェーズリセット） |
|------|-------------|-------------------|
| 変更の範囲 | 単一タスクの実装アプローチのみ | DB スキーマ / API 仕様 / データモデル定義そのもの |
| 既存実装への影響 | 他の完了済みタスクに影響しない | 他のタスクのコード書き直しが必要 |
| design.md の変更 | 不要（Restrictions への追記のみ） | 必要 |
| 典型例 | DTO フィールド使用法の解釈違い、使用中の既存コンポーネントの変更 | テーブル定義の変更、レスポンス型の追加・削除、FK 仕様の変更 |

### A. design.md の範囲内で実装調整（軽微なケース）

- 調整内容を `_Prompt` の Restrictions に追記し、rework で parallel-worker に戻す
- design.md は変更しない

### B. design.md の変更が必要（根本的な問題） — フェーズリセット

**design.md を変更する必要がある場合、これまでの実装をすべて破棄し Phase 2 からやり直す。** 部分的な修正は許可されない。

フェーズリセット手順:
1. **Phase 5 を中断**: 進行中のタスク（`[-]`）を `[ ]` に戻す
2. **実装コードを破棄**: Phase 5 で実装・コミットしたコードを `git revert` で取り消す
3. **tasks.md を削除**: `.spec-workflow/specs/{spec-name}/tasks.md`（Phase 4 成果物）を削除
4. **design.md を修正**: Phase 2 に戻って design.md を修正
5. **再レビュー**: spec-review（check）で design.md を再検証
6. **再承認**: 承認ワークフロー経由で design.md の再承認を取得
7. **Phase 3-4 の再実行**: `/spec-test-design` で test-design.md を再作成、次に `/spec-tasks` で tasks.md を再作成
8. **Phase 5 の再実行**: `/spec-implement` で最初から実装を再開

**注記:** フェーズリセットのコストは高い。これを避けるため、Phase 2 で徹底的な設計レビュー（DB スキーマ、API 設計、データモデル、エラーハンドリング）を行う。

## review-worker での検証

コードレビュー時、review-worker は `design.md` を読み、以下をチェックする:

- 実装された DB マイグレーションが design.md のスキーマ定義と一致するか
- 実装されたエンドポイントのパス、メソッド、リクエスト/レスポンス型が design.md の API 定義と一致するか
- 実装された Model / DTO のフィールドが design.md のデータモデル定義と一致するか
- design.md で定義されていない追加がないか
