# リグレッションテストポリシー

ユーザーバグレポートからテストケースへの変換プロセスと、
受け入れ基準をリグレッションテストとして定着させるための運用方針。
P7-01, P7-02 に対応する。

## RT1: バグレポート → テストケース変換 (P7-01)

ユーザーから報告されたバグは、修正前に**必ず**再現テストケースを作成する。
修正後もテストケースを維持し、同一バグの再発を防止する。

### 変換フロー

```
1. バグレポート受領
   ↓
2. 再現条件の特定
   ↓
3. 失敗するテストケースを作成（RED）
   ↓
4. バグを修正（GREEN）
   ↓
5. テストケースをリグレッションスイートに追加
   ↓
6. CI で自動実行されることを確認
```

### テストケースの命名規則

バグ由来のテストケースは Issue 番号で追跡可能にする:

```rust
// Rust
#[test]
fn regression_issue_123_login_fails_with_special_chars() {
    // GH#123: ユーザー名に特殊文字を含むとログインに失敗する
    // ...
}
```

```typescript
// TypeScript
it('regression #123: login fails with special chars in username', () => {
  // GH#123: ユーザー名に特殊文字を含むとログインに失敗する
  // ...
});
```

### テストケースの分類

| バグの影響範囲 | テストレベル | 配置先 |
|--------------|------------|--------|
| 単一関数/メソッドの不具合 | Unit Test | `src/` 内のテストモジュール |
| コンポーネント間の結合不具合 | Integration Test | `tests/` |
| ユーザージャーニーに影響する不具合 | E2E Test | `e2e/` or `tests/e2e/` |

### Issue テンプレートとの連携

バグ Issue には以下のフィールドを含めることを推奨:

```markdown
## バグレポート

### 再現手順
1. ...
2. ...

### 期待される動作
...

### 実際の動作
...

### テストケース
- [ ] 再現テスト作成済み（テストファイル: ）
- [ ] リグレッションスイートに追加済み
```

## RT2: 受け入れ基準のリグレッションテスト化 (P7-02)

test-design.md の Requirements-Test Traceability Matrix で定義された受け入れ基準は、
実装後も**永続的なリグレッションテスト**として維持する。

### 原則

1. **削除禁止**: 受け入れ基準に基づくテストは、仕様変更なしに削除してはならない
2. **仕様変更時**: 仕様変更が発生した場合、テストを削除するのではなく新しい仕様に合わせて更新する
3. **全件 CI 実行**: 受け入れ基準テストは `cargo test` / `npm test` のデフォルト実行対象に含める
4. **Traceability 維持**: 各テストは Requirement ID（REQ-N）をコメントまたは命名規則で追跡可能にする

### Traceability Matrix の活用

test-design.md の Traceability Matrix:

```markdown
| Requirement ID | UT Specs | IT Specs | E2E Specs | Notes |
|---------------|----------|----------|-----------|-------|
| REQ-1 | UT-1.1, UT-1.2 | IT-1 | E2E-1 | |
```

**チェック方法**: 全 REQ-N に最低 1 つの UT + 関連する IT or E2E が紐づいていることを確認する。
未カバーの REQ がある場合は、Phase Review で検出し追加テストを要求する。

### リグレッションテストの定期確認

doc-freshness.md の鮮度チェック対象に test-design.md が含まれている（120日閾値）。
テスト仕様と実装の乖離が検出された場合は、テストの更新を優先する。

## RT3: リグレッションスイートの管理

### スイートの構成

| スイート | 実行タイミング | 内容 |
|---------|-------------|------|
| Unit Regression | コミット前 / PR CI | 全ユニットテスト（バグ由来含む） |
| Integration Regression | Phase Review / E2E Gate | 全統合テスト |
| E2E Regression | Final E2E Gate | 全 E2E テスト |

### スイートの健全性指標

| 指標 | 健全な状態 | 要注意 |
|------|----------|--------|
| 全テスト PASS 率 | 100% | 99% 未満は即対応 |
| flaky テスト率 | 0-2% | 5% 超で FT5 隔離対象 |
| テスト実行時間 | PR CI で 5分以内 | 10分超は並列化検討 |
| バグ再発率 | 0% | 再発はテストケース不足を示す |

### spec-workflow との連携

- **Phase 3（test-design）**: 受け入れ基準を UT/IT/E2E に分解し Traceability Matrix に記録
- **Phase 5（implement）**: TDD の RED フェーズでテストを先行作成
- **Phase Review**: Traceability Matrix の全 REQ カバレッジを検証
- **バグ修正時**: RT1 フローに従い再現テスト → 修正 → リグレッション追加
