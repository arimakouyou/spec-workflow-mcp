# Spec Dependency Graph

A vocabulary for managing dependencies between spec documents declaratively. Makes the upstream-to-downstream traceability of requirements.md -> design.md -> test-design.md -> tasks.md machine-readable.

This serves as the input for `/spec-impact-analyze` (F: impact analysis) and `/spec-verify` (I: consistency verification). The existing task-level metadata (`_Requirements:` / `_DependsOn:` / `_Leverage:`) is retained, and this declares dependencies **between spec-document files** orthogonally to that.

## SD1: Identifier System

ID conventions for referencing sections within spec documents in a machine-readable way. Codifies naming that respects the existing templates.

| File | ID Format | Example | Relationship to Existing Rule |
|---------|---------|-----|----------------|
| `requirements.md` | `REQ-N.M` | `REQ-1.1`, `REQ-2.3` | Corresponds to Acceptance Criterion M of Requirement N. Uses the same coordinate system as the existing `_Requirements:` values such as `1.1`, `2.1` |
| `design.md` (Components and Interfaces) | `DES-N` | `DES-1`, `DES-2` | Makes the existing `### Component N` explicit as DES-N. Write the heading in the form `### DES-1: ComponentName` |
| `design.md` (Data Models) | `MOD-N` | `MOD-1`, `MOD-2` | Makes the existing `### Model N` explicit as MOD-N (optional) |
| `design.md` (API / Endpoint) | `API-N` | `API-1` | Identifier when an API definition exists (optional) |
| `test-design.md` (Unit Test) | `UT-N.M` | `UT-1.1` | Same as the existing rule |
| `test-design.md` (Integration Test) | `IT-N` | `IT-1` | Same as the existing rule |
| `test-design.md` (E2E Test) | `E2E-N` | `E2E-1` | Same as the existing rule |
| `tasks.md` (Task) | `N.M` | `1.1`, `2.3` | Same as the existing rule (parsed by task-parser.ts) |

- The way IDs are made explicit **differs by phase**:
  - **requirements.md**: Requirement headings use the form `### REQ-N: Title` (e.g., `### REQ-1: User Login`). Acceptance Criteria are listed as a numbered list, with a `<!-- REQ-N.M -->` comment at the end of each line to make the REQ-N.M identifier explicit (see `requirements-template.md`)
  - **design.md**: Component heading is `### DES-N: ComponentName`, Data Model is `### MOD-N: Name`, API is `### API-N: Name` (e.g., `### DES-1: UserRepository`)
  - **test-design.md**: `#### UT-N.M: Name` / `### IT-N: Name` / `### E2E-N: Name` (same as the existing rule)
  - **tasks.md**: List items of the form `- [ ] N.M Title` (same as the existing rule, parsed by `task-parser.ts`)
- A downstream spec's `depends_on.refs` can reference both **REQ-N (bare, referring to the entire Requirement)** and **REQ-N.M (referring to an individual Acceptance Criterion)**. `refs: [REQ-1]` means all ACs under REQ-1; `refs: [REQ-1.1, REQ-1.2]` means individual ACs only
- When adding IDs to an existing spec retroactively, treat it as a Minor change. If there are no downstream references, IDs need not be added (see SD3)
- The M in UT-N.M is a sub-number of N (test case M of Component N) and is **independent** of the M in REQ-N.M (Acceptance Criterion M)

## SD2: Frontmatter Schema

Place a YAML frontmatter at the top of each spec-document file.

```yaml
---
spec_id: {spec-name}              # kebab-case, must match the directory name under .spec-workflow/specs/
phase: requirements | design | test-design | tasks
version: 1                         # optional, increment by 1 on major revisions (used for F's cache decision)
depends_on:                        # references to upstream spec documents. requirements.md uses an empty array
  - file: requirements.md
    refs: [REQ-1.1, REQ-1.2, REQ-2.1]
---
```

### Typical depends_on per phase

| phase | Typical depends_on |
|-------|---------------------|
| `requirements` | `[]` (most upstream) |
| `design` | The REQ- entries in `requirements.md` that this design implements |
| `test-design` | REQ- entries in `requirements.md` (verification target) + DES- entries in `design.md` (components under test) |
| `tasks` | DES- entries in `design.md` (implementation target) + UT-/IT-/E2E- entries in `test-design.md` (tests to satisfy) |

### How to write refs

- `refs` is an array of strings. **Only IDs that actually exist in the upstream spec document** are allowed (verified by SD4)
- Do not write the same upstream file in multiple lines (`file: requirements.md` is unique)
- If refs would be an empty array, omit the corresponding `depends_on` element entirely (avoid superfluous declarations)

## SD3: Backward Compatibility (Opt-in for Legacy Specs)

frontmatter is **required for new specs** and **opt-in for existing specs**.

- **New spec documents** generated by `/spec-requirements`, `/spec-design`, `/spec-test-design`, and `/spec-tasks` must include frontmatter
- Existing spec documents (those without frontmatter) are treated as `phase: legacy`
- `/spec-impact-analyze` and `/spec-verify` report "no dependency information" for spec documents without frontmatter and skip static analysis (`not_available` status). They do not raise an error
- To upgrade an existing spec to use frontmatter, simply add the frontmatter manually (no need to modify existing body content)

## SD4: Reference Integrity

IDs written in `depends_on.refs` must exist in the referenced file.

- `/spec-verify` verifies this
- References to non-existent IDs are **reported as `fail`** (blocking, not warning)
- When the referenced file is a legacy file without frontmatter, detect the existence via **ID markers** in the body. Valid detection sources per ID type (any one is sufficient — OR judgment):
  - **REQ-N** (requirements.md): a `### REQ-N:` heading exists
  - **REQ-N.M** (requirements.md): (a) an Acceptance Criterion line with a `<!-- REQ-N.M -->` comment, or (b) the **M-th** numbered list item under the `### REQ-N:` heading (where `.M` corresponds to the Acceptance Criterion number) — valid if either (a) or (b) exists
  - **DES-N / MOD-N / API-N** (design.md): a corresponding `### DES-N:` / `### MOD-N:` / `### API-N:` heading exists
  - **UT-N.M / IT-N / E2E-N** (test-design.md): a corresponding `#### UT-N.M:` / `### IT-N:` / `### E2E-N:` heading exists

## SD5: No Cycles

Do not create circular dependencies via `depends_on` (paths such as requirements -> design -> requirements). References that go backwards in the phase order `requirements -> design -> test-design -> tasks` are prohibited.

- `/spec-verify` verifies the DAG property
- If a cycle is detected, it is blocking (stops the start of implementation)

## SD6: Coexistence with Task-level Metadata

The metadata at the **task level** (individual task lines in tasks.md) retains the existing rules:

| Metadata | Meaning | Example |
|-----------|------|-----|
| `_Requirements:` | The REQ-N.M that this task satisfies | `_Requirements: 1.1, 2.1` |
| `_DependsOn:` | Other tasks (task-id) that this task depends on | `_DependsOn: 1.1` |
| `_Leverage:` | Files this task reuses | `_Leverage: src/types/base.ts` |
| `_PhaseReview:` | Marker for a Phase Review task | `_PhaseReview: true` |
| `_TDDSkip:` | Marker for skipping TDD | `_TDDSkip: true` |
| `_TestFocus:` | Free-form description of test focus areas | `_TestFocus: boundary values` |

The **inter-spec-document** `depends_on` frontmatter declares the DES-/UT- in design.md / test-design.md that tasks.md as a whole depends on. Per-task REQ linkage continues to use `_Requirements:` (this is **orthogonal information at a different granularity**, not duplicated management).

## SD7: Change Propagation Semantics

When `depends_on` is declared, defines the semantics of how upstream changes propagate to downstream (the criteria for `/spec-impact-analyze`).

| Type of Change | Effect on Downstream | Impact Analysis Classification |
|-----------|-------------|--------------------|
| **Adding a new** upstream ID | Just adds a new reference candidate downstream | `gray` (informational) |
| **Removing** an upstream ID | Downstream `refs` can no longer reference it — removal required | `amber` (needs review when references exist) |
| **Substantive change** to the conditions/intent of an upstream ID (rewrite of Acceptance Criteria, etc.) | Downstream design / test / implementation lose their premises | `amber` (needs review when references exist) |
| **Wording fluctuation / typo fix** of an upstream ID (functional conditions unchanged) | Downstream is unaffected | `green` (auto-applicable) |
| Changes to upstream IDs **not referenced** | Downstream is unrelated | `gray` (informational) |

The judgment between "substantive change" and "wording fluctuation" is currently delegated to LLM judgment (`/spec-impact-analyze` decides). It may shift to mechanical diff detection (keyword extraction, etc.) in the future, but heuristics are not fixed at this stage.

## Related Skills

A group of independent skills that consume this dependency-graph definition (all read-only and do not gate the workflow):

| Skill | Role |
|-------|------|
| `/spec-impact-analyze` | Takes the diff of upstream changes (e.g., requirements.md) as input and reports the downward propagation, classifying it as green/amber/gray per SD7 |
| `/spec-verify` | Uses SD1-SD7 to verify frontmatter presence, refs integrity (SD4), DAG property (SD5), and the REQ -> test -> task coverage |
| `/spec-graph` | Generates a mermaid dependency graph from frontmatter (file level / id level). Used for a visual overview |

These correspond to the three aspects of the Harness-as-Code approach (change propagation / consistency verification / visualization) and are added as auxiliary skills that extract value without touching the rules directly.
