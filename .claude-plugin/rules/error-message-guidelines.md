# Error Message Quality Guidelines

Standards for including repair steps and fix examples in error messages emitted by
custom tests, architecture tests, and lint scripts. Corresponds to P6-05.

## EM1: Test Assertion Messages

Assertion messages in custom tests must include the following three elements:

1. **What happened** (WHAT): a concrete description of the detected problem
2. **What is expected** (EXPECTED): the correct state or value
3. **How to fix it** (FIX): concrete repair steps

### Rust Example

```rust
assert!(
    violations.is_empty(),
    "Architecture violation detected:\n{violations}\n\n\
     Expected: dependencies from {from_layer} to {to_layer} are prohibited.\n\
     Fix: Remove `use crate::{to_module}`, or \
     review the dependency direction rule in design.md Module Boundaries."
);
```

### TypeScript/JavaScript Example

```typescript
expect(result).toBe(expected,
  `FAIL: ${description}\n` +
  `Expected: ${expected}\n` +
  `Fix: ${repairInstruction}`
);
```

## EM2: Architecture Test Error Messages

Tests generated by `/generate-arch-tests` must include the following information:

- Path of the offending file
- The violated dependency direction rule (the prohibited From -> To rule)
- The fix action (remove the import or review design.md)

### Expected Output Example

```
Architecture violation detected:
  src/services/payment.rs -> handlers (services -> handlers is prohibited)

Fix: Remove the `use crate::handlers` import, or
review the dependency direction rule in design.md Module Boundaries.
```

## EM3: CI Step Error Output

Each step in a CI workflow must satisfy the following:

- The step name is clear and describes its action (e.g., "Format check", "Security audit")
- Set the `id` field so it can be referenced from the PR-comment script
- Capture error output to a file (`2>&1 | tee /tmp/output.txt`)
- Display the result as a structured Markdown table in the PR comment

The CI template generated by setup-ci complies with this standard.

## EM4: Custom Lint / Validation Scripts

Recommended error output format for custom validation scripts:

```
{SEVERITY}: {rule_id} — {description}
  File: {file_path}:{line_number}
  Fix: {repair_instruction}
```

| Field | Required | Description |
|-----------|------|------|
| SEVERITY | Yes | ERROR / WARN / INFO |
| rule_id | Yes | Rule ID (e.g., FT5, EM1) |
| description | Yes | Description of the problem |
| File | Recommended | File path and line number |
| Fix | Yes | Concrete repair steps |

### Output Examples

```
WARN: FT5 — Quarantined test exceeded 30 days
  File: tests/integration/payment_test.rs:42
  Fix: Either remove #[ignore] and fix the test, or delete the test itself

ERROR: EM1 — Assertion message does not include repair steps
  File: tests/unit/auth_test.rs:15
  Fix: Add a message that includes "Fix: ..." as the second argument to assert!
```
