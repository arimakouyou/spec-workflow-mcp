# 設計原則

コードレビューと実装時に適用する設計原則。

## 関心の分離

- 各関数、構造体、モジュールは単一の責務に集中すべきである
- ハンドラにビジネスロジックを書かない。ハンドラは「入力の受け取り → サービス/リポジトリの呼び出し → レスポンスの構築」に限定する
- バリデーション、データ変換、ビジネスルールは適切なレイヤーに配置する
- 「この関数が何をするか」を1文で説明できない場合は分割を検討する

## 依存関係の方向

- 上位レイヤーが下位レイヤーに依存する（handler → service/repository → model）
- 逆方向の依存（例: model が handler を参照）は禁止
- 循環依存を作らない
- 外部サービスへの依存はトレイトで抽象化し、具象型への直接依存を避ける

## パブリック API の最小化

- 不必要な `pub` を追加しない。モジュール外からアクセスする必要がなければプライベートのままにする
- 内部の実装詳細（ヘルパー関数、中間型）を公開しない
- `pub(crate)` を使用して可視性を必要最小限に制限する

## 一貫したエラーハンドリング

- プロジェクト全体で共有するエラー型（例: `AppError`）を使用し、各レイヤーからのエラーは `From` で変換する
- `unwrap()` / `expect()` はテストコードまたは初期化時の不変条件でのみ許可。ビジネスロジックでは `?` 演算子を使用する
- エラーメッセージには「何が起きたか」と「何が期待されていたか」を含める
- ユーザー向けエラーと内部ログエラーを分離する（内部の詳細をクライアントに返さない）

## 命名の適切性

- 型名、関数名、変数名は意図を正確に表現すべきである
- 省略形を避け、検索可能な名前を使用する（`usr` → `user`; `ctx` は慣習的に許容）
- bool 変数・関数には `is_`、`has_`、`can_` などのプレフィックスを付けて意図を明確にする
- 否定形の命名を避ける（`is_not_empty` → `is_empty` の否定で表現する）

## DRY（Don't Repeat Yourself）

- 同じロジックが2箇所以上に存在する場合は集約を検討する
- ただし、偶然の類似性（たまたま同じに見えるコード）を無理に集約しない。「同じ理由で変更されるか？」で判断する
- 関数の抽出、トレイトの抽出、ジェネリクスの順に集約を検討し、最もシンプルな手段を選択する

## YAGNI（You Aren't Gonna Need It）

- 現時点で必要のない機能、抽象化、設定オプションを先回りして実装しない
- 「将来使うかもしれない」は実装の理由にならない。必要になった時に追加する
- 過度な汎用化よりも、具体的で理解しやすい実装を優先する
