# Staged Enforcement Model and Rule Promotion Criteria

Defines a staged enforcement model based on rule maturity. A rule starts as
documentation, and the enforcement level is automatically promoted as violations accumulate.

## Enforcement Level Definitions

| Level | Name | Enforcement Mechanism | Behavior on Violation |
|-------|------|---------|-------------|
| L1 | Documentation | Described in a rule file (`.claude-plugin/rules/`) | Agents reference it but it is not enforced |
| L2 | AI Review | Inspected through review-worker review categories (A-G) | Reported as findings; rework/escalate |
| L3 | CI Tooling | Mechanically inspected by GitHub Actions CI jobs | CI failure blocks merge |
| L4 | Structural Tests | Verified by test code such as `tests/architecture.rs` | `cargo test` failure blocks the build |
| L5 | Compiler / Type System | Enforced via the language type system or compiler errors | Cannot compile |

## Rule Promotion Criteria

Defines the conditions and procedure for raising a rule's enforcement level.

### Promotion Conditions

| Promotion Path | Condition | Decision-maker |
|---------|------|--------|
| L1 -> L2 | The rule is established and is repeatedly raised in reviews | Team lead |
| L2 -> L3 | The same rule violation has been detected three or more times in AI reviews | Team lead + CI owner |
| L3 -> L4 | A structural violation exists that CI checks cannot detect | Architect |
| L4 -> L5 | The invariant can be expressed in the type system | Architect |

### Promotion Procedure

1. **Proposal**: Collect violation logs and assess the validity of promotion
2. **Create ADR**: Record an ADR for the promotion decision via the `/adr` skill
3. **Implementation**: Add the tool configuration / test code for the destination level
4. **Verification**: Confirm that existing code conforms to the new enforcement level
5. **Apply**: Integrate into CI / tests so that violations are detected

### Automatic Promotion Proposals (P3-04)

The weekly scheduled quality check (`--with-scheduled`) accumulates violations, and when the threshold is exceeded, it automatically proposes a promotion.

**Accumulation method**: Apply the `[Quality]` label to issues from weekly CI. When a certain number of issues with the same rule ID accumulate, the rule becomes a promotion candidate.

| Promotion Path | Auto-proposal Trigger | Proposal Content |
|---------|---------------|---------|
| L1 -> L2 | The same pattern is reported on 2 or more issues | Propose adding it to review-worker check items |
| L2 -> L3 | The same rule ID appears 3 or more times in review-worker findings | Propose adding a check to a CI job |
| L3 -> L4 | Structural violations not detected by CI occur 2 or more times | Propose adding tests via `/generate-arch-tests` |

**Proposal format**: Output the following as an issue comment or as a new issue:

```
## Promotion Proposal

- Rule: {rule-id} ({rule-name})
- Current enforcement level: L{N}
- Proposed promotion target: L{N+1}
- Rationale: {summary of the most recent M violations}
- Recommended action: {concrete implementation steps}
```

### Demotion Conditions

| Condition | Action |
|------|----------|
| The rule no longer matches reality | Demote from L3/L4 to L2, reverting to AI review only |
| There are many false positives | Temporarily demote to L1 and re-examine the rule itself |
| Project policy change | Record retirement via ADR and remove the rule from the corresponding level |

## Coordination with review-worker

review-worker is the primary enforcer at L2 (AI Review). Findings in each category (A-G) are classified into the following severities:

| Severity | Target Categories | Action | Promotion Candidate |
|----------|------------|----------|---------|
| Minor | A (Style), G (API Docs) | auto-fix | L3 promotion candidate (mechanically fixable) |
| Moderate | B (Design), C (Security), E (Tests), E2 (TDD) | rework via parallel-worker | L4 promotion candidate (can be made into structural tests) |
| Critical | D (Spec), F (Design Conformance) | escalate to user | L5 promotion candidate (consider whether it can be expressed via types) |

## Auto-fix PR Generation (P3-10)

A mechanism in which agents automatically create fix PRs for quality issues detected by the weekly scheduled check.

### Issues That Can Be Auto-fixed

| Issue Type | Fix Method | Example PR Title |
|---------|---------|-------------|
| Format violation | `cargo fmt` / `prettier --write` | `fix: auto-format code` |
| Unused dependency | Remove from `Cargo.toml` | `chore: remove unused dependencies` |
| Missing doc comment | Apply suggestions from `/generate-api-docs` | `docs: add missing doc comments` |
| Stale documentation | Update content to match the current state | `docs: update stale documentation` |

### Auto-fix Flow

1. Weekly CI (`scheduled-quality.yml`) detects violations and creates an issue with `[quality]` + `[automated]` labels
2. `auto-fix-quality.yml` triggers Claude Code on the issue creation event and runs `/handle-issue` automatically
3. Implement the fix on a branch
4. Create the PR with `/create-pr --closes {issue-number}`
5. Quality verification by CI + review-worker
6. Merge after approval (auto-merged when `--with-auto-merge` is enabled)

> **CI workflow setup**: `/setup-ci --with-auto-fix` generates `auto-fix-quality.yml`.
> Prerequisite: the `ANTHROPIC_API_KEY` secret must be configured.

### Issue-only Case (PARTIAL handling)

Even when the auto-fix PR mechanism is not yet in place (i.e., `--with-auto-fix` is not applied), the PARTIAL judgment for P3-10 / P8-07 can be obtained with issue creation alone.
For complete auto-fix PR generation, add the CI workflow with `/setup-ci --with-auto-fix` and configure the `ANTHROPIC_API_KEY` secret.

In Phase Review (step 3.5), the following enforcement levels apply:

1. **L4 Structural Tests**: step 3.5.1 runs architecture tests automatically via `cargo test`
2. **L3 CI**: step 3.5.1.5 integrated verification runs CI-equivalent checks
3. **L2 AI Review**: step 3.5.2 Expert Team Review provides multi-perspective review
4. **L3 CI**: step 3.5.1.6 CVE Audit mechanically inspects vulnerabilities
