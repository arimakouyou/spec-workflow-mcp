# セキュリティコーディング標準

コードレビューと実装時に適用するセキュリティ標準。OWASP Top 10 に基づき、認証・認可を含む。

## A1: インジェクション

- SQL: ORM クエリビルダ（例: Diesel）を通じてクエリを構築する。外部入力を文字列結合で生 SQL に埋め込まない
- コマンドインジェクション: ユーザー入力を `Command::new()` や `exec` 系呼び出しに直接渡さない。`.arg()` を使用して引数を個別に渡す
- パストラバーサル: ファイルパスにユーザー入力を含める場合、ディレクトリトラバーサル（`../`）に対するバリデーションを行う

## A2: 認証の不備

- 認証が必要なエンドポイントには認証ミドルウェアを適用する（例: `route_layer`）
- パスワードを平文で保存しない。bcrypt / argon2 などのハッシュ関数を使用する
- セッショントークン / JWT は暗号学的に安全な乱数値で生成する
- トークンに有効期限を設定し、期限切れのトークンを拒否する

## A3: アクセス制御の不備

- リソースアクセスに対するオーナーチェックを実装する（ユーザーは自分自身のデータのみ閲覧・更新できる）
- IDOR（安全でない直接オブジェクト参照）: パスパラメータの ID だけでアクセスを許可しない。認証済みユーザーとの関連を検証する
- ロールベースの認可が必要な場合、ミドルウェアまたはガード関数に集約する
- 管理者専用エンドポイントが一般ユーザーからアクセスできないことを検証する

## A4: 機密データの露出

- レスポンスにパスワードハッシュ、内部 ID、スタックトレース、DB エラー詳細を含めない
- DTO を使用してレスポンス型を明示的に定義する。Model オブジェクトを直接返さない
- 機密情報（パスワード、トークン、個人データ）をログに出力しない
- 本番環境では、クライアントが内部実装を推測できないような汎用的なエラーメッセージを使用する

## A5: 入力バリデーション

- リクエストボディ、パスパラメータ、クエリパラメータからのすべての入力をバリデーションする
- 文字列長に上限を設定する（DoS 防止）
- 型変換エラー（例: 文字列 → 数値）には 400 Bad Request を返す
- メールアドレス、URL、日付などの形式バリデーションには専用ライブラリを使用する

## A6: セキュリティヘッダと CORS

- CORS の許可オリジンを明示的に設定する（`CorsLayer::permissive()` は開発環境専用）
- Content-Type を検証し、予期しない形式のリクエストを拒否する

## A7: マスアサインメント

- DTO → Model 変換時、クライアントが更新すべきでないフィールド（`id`、`created_at`、`role` など）が変更されないようにする
- `AsChangeset` を使用する場合、更新対象のフィールドを明示的に指定する

## A8: レート制限

- パブリックエンドポイント（ログイン、登録、パスワードリセット）にレート制限を設計する
- ブルートフォース対策として繰り返し失敗後のロックアウトを検討する

## A9: 依存関係の脆弱性

- `cargo audit` を使用して既知の脆弱性を定期的にチェックする
- 未使用の依存関係を削除する

## A10: ログとモニタリング

- 認証失敗、認可失敗、バリデーションエラーをログに記録する
- ログに十分なコンテキストを含める（リクエスト ID、ユーザー ID）
- ただし、機密情報はマスクする（A4 を参照）
