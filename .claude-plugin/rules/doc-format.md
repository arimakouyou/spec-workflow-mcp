# Spec Document Format (v2)

The single definition of the spec document grammar. `scripts/spec-lint.sh` enforces this file; templates under `templates/docs/` instantiate it. When this file and a template disagree, this file wins and the template is a bug.

Core rule: **every fact has exactly one owning document. Every other document refers to it by ID and never restates it.**

## 1. Files

| Path (under `.spec-workflow/`) | Owner | Approved |
|---|---|---|
| `steering/product.md`, `steering/tech.md`, `steering/structure.md` | steering-doc | yes |
| `specs/{spec}/request-spec.md` | spec-request-spec | yes |
| `specs/{spec}/evidence/manifest.md`, `evidence/EV-*.md` | spec-investigate | no (frozen) |
| `specs/{spec}/requirements.md` | spec-requirements | yes |
| `specs/{spec}/design.md` | spec-design | yes |
| `specs/{spec}/test-design.md` | spec-test-design | yes |
| `specs/{spec}/tasks.md`, `trace.md` | generated by `spec-plan.sh` / `spec-trace.sh` | no (never hand-edited) |
| `specs/{spec}/changes.md` | spec-change | no (record) |
| `specs/{spec}/refactor-backlog.md`, `task-logs/` | `spec-git.sh` | no |

All files are UTF-8 with LF line endings. Approved documents are immutable except through `/spec-change`.

## 2. Common syntax

### 2.1 Frontmatter

Every approved document starts with YAML frontmatter:

```yaml
---
spec: {spec-name}
doc: request-spec | requirements | design | test-design
---
```

request-spec additionally carries `task_type` (§4.1). No other keys. Dependencies between documents are fixed (§6) and are not declared in frontmatter.

### 2.2 Definitions

A definition is a heading `### <ID>: <Name>` (level 3). Two exceptions:

- UT / CT definitions are level-4 headings `#### <ID>: <Title>` under a level-3 group heading `### DES-N` (the group heading carries the bare ID only, never the component name).
- Acceptance criteria are list items `- REQ-N.M: <EARS sentence>` inside a `### REQ-N` block.

A definition block spans from its heading to the next heading of the same or higher level. IDs are never renumbered and never reused; deleted numbers stay vacant.

### 2.3 Fields

Fields are list items directly under a definition heading, before any sub-heading:

```markdown
- Field: value
- ListField: ID-1, ID-2
- Nested:
  - item one
  - item two
- Code:
  ```rust
  ...
  ```
```

- Field names are fixed per block type (§4). An unknown field is L16.
- A list value is comma-separated on one line. `-` means "none" and is only allowed where §4 says so.
- A code field is followed by exactly one fenced block (indented 0 or 2 spaces).

### 2.4 ID syntax

| ID | Pattern | Defined in |
|---|---|---|
| RQ | `RQ-\d+` | request-spec |
| EV | `EV-[a-z-]+-\d{3}` | evidence/ |
| REQ / AC | `REQ-\d+` / `REQ-\d+\.\d+` | requirements |
| NFR / JRN | `NFR-\d+` / `JRN-\d+` | requirements |
| DES / MOD / API / TST / DEP / TOOL / KD | `DES-\d+` … `KD-\d+` | design |
| UT / CT | `UT-\d+\.\d+` / `CT-\d+\.\d+` (first number = the DES under test) | test-design |
| IT / ST / E2E | `IT-\d+` / `ST-\d+` / `E2E-\d+` | test-design |
| SMK | `SMK-L1`, `SMK-L[234]-API-\d+` | generated |
| Task keys | `P0-TOOLS`, `DES-N`, `TST-N`, `P\d+-(IT\|ST\|SMK\|REFACTOR\|REVIEW)`, `FINAL` | generated |
| RF / CHG / BUG | `RF-\d{3}` / `CHG-\d{3}` / `BUG-[\w-]+` | backlog / changes / external |

### 2.5 References

- **Plain reference**: the bare ID, e.g. `REQ-4.5`, `DES-6`, `API-2`.
- **Qualified symbol**: a backticked `<ID>:<path>` naming a symbol owned by that block, e.g. `` `DES-6:render_file` ``, `` `MOD-21:RenderedDocument` ``, `` `MOD-21:RenderedDocument::TooLarge` ``, `` `TST-3:spawn` ``. `<path>` is `Ident(::Ident)*`. The first segment must be declared in the owner's code block (L06); later segments must be members of it (L07).
- Symbols declared by a code block:
  - **MOD `Definition`**: the type name. Its members are the enum variants or the struct fields.
  - **DES / TST `Interfaces`**: every trait name, every `impl` target type, and every top-level `fn`. The members of a trait or impl are its methods. A method name alone (`DES-4:create`) also resolves when it is unique within the block. Otherwise write `DES-4:TodoService::create`.
- **Line numbers are forbidden everywhere** (`file.ext:123`, `#L123`) (L03). The only exception is `sources:` in evidence frontmatter. There each entry is `path:Lx-Ly@<commit>` for code, or a URL for external documentation (category `lib`).

### 2.6 Code tokens

A *code token* is a backticked span that is not a qualified symbol and not a literal, or an unbackticked `Ident::Ident` path.

- Literals: numbers, quoted strings, JSON objects/arrays, URL paths starting with `/`, HTTP methods, status codes, and the prelude words `Ok Err Some None true false null`.
- Code tokens are allowed **only** inside design code fields (`Interfaces`, `Definition`) and the design fields `Held-as`, `Implements`, `Files`.
- Anywhere else in design they are L05. In request-spec, requirements and test-design they are L04. Refer to the owner with a qualified symbol instead.

## 3. Steering

### 3.1 product.md

Sections: `## Purpose`, `## Users`, `## Principles`, `## Non-Goals`. Prose only.

### 3.2 tech.md

tech.md owns project-wide technical facts. Required sections:

```markdown
## Stack
| Item | Choice | Version |
|---|---|---|
| language | rust | 1.93 |

## Test Commands
| Layer | Command |
|---|---|
| UT | cargo test --lib |
| CT | cargo test --target wasm32-unknown-unknown |
| IT | cargo test --test '*' |
| ST | cargo test --test 'st_*' |
| E2E | npx playwright test |

## Test Layout
- UT: {stem}_tests.rs beside the source file, included via #[cfg(test)] #[path] mod tests
- CT: tests/ct_{component}.rs
- IT: tests/it_{name}.rs

## Wiring Files
- Cargo.toml
- crates/*/Cargo.toml

## Health
- Path: /health

## Sigcheck
- Language: rust
```

- A layer the project does not use is written as `| CT | - |`.
- `Sigcheck` is `rust`, `dotnet`, or `unsupported (<reason>)`. A missing `Sigcheck` section is L23.
- In greenfield projects these values are *planned* values. They become real when the P0 bootstrap completes (§7).

### 3.3 structure.md

Sections: `## Directories` (table `| Path | Purpose |`), `## Placement Rules` (table `| Kind | Location |`).

## 4. Spec documents

### 4.1 request-spec.md

```markdown
---
spec: todo-api
doc: request-spec
task_type: feature-add
---
# Request: <title>

## Overview
<prose>

## Requests
### RQ-1: <name>
- Actor: <who>
- Goal: <what>
- Flow:
  - <step>
- Exceptions:
  - <case>

## Out of Scope
- <prose item>
```

- `task_type` is one of `feature-add | feature-modify | bugfix | refactor | legacy-migration | greenfield | legacy`.
  - `legacy` requires `legacy_reason:` and skips Phase 0.5.
  - `greenfield` collects only external-library evidence (`EV-lib-*`).
- `Preconditions`, `Postconditions` and `Alternate` are optional fields.
- Technology and runtime sections are forbidden here (L15); they belong to tech.md or design `DEP`/`TOOL`.

Required evidence categories per `task_type`:

| task_type | Required EV categories |
|---|---|
| feature-add | code, contract |
| feature-modify | code, contract, tests |
| bugfix | code, tests, regressions |
| refactor | code, tests |
| legacy-migration | code, contract, tests |
| greenfield | lib |
| legacy | — |

### 4.2 requirements.md

```markdown
## Requirements
### REQ-1: <name>
- Source: RQ-1
- Story: As a <role>, I want <capability>, so that <benefit>
- Evidence: EV-code-001
- REQ-1.1: WHEN <event> THEN the system SHALL <response>
- REQ-1.2: IF <condition> THEN the system SHALL <response>

## Non-Functional
### NFR-1: <name>
- Category: performance | security | reliability | usability | testability | compatibility
- Criterion: <measurable statement>
- Rationale: <why this number>

## Journeys
### JRN-1: <name>
- Covers: REQ-1, REQ-2
- Steps:
  - <user action>

## Out of Scope
- RQ-3: <reason>
```

- Each AC is one EARS sentence with a single observable outcome.
- Every `RQ` is either a `Source` of some REQ or listed under `## Out of Scope` (L11).
- Test layers are **not** declared here. test-design owns them.

### 4.3 design.md

Sections appear in this order. All are required except `Excluded Tests`.

```markdown
## Overview
## Phases
- P0: <purpose>
- P1: <purpose>

## Layers
| Layer | Paths | Depends on |
|---|---|---|
| domain | crates/app/src/domain/** | - |
| http | crates/app/src/http/** | domain |
| bootstrap | crates/app/src/main.rs | domain, http |

## Components
### DES-1: <Name>
- Kind: logic | types | adapter | ui | wiring | config
- Layer: domain                  # - for Kind config
- Phase: 1
- Files: crates/app/src/domain/todo.rs
- Depends: DES-2, DES-3          # or -
- Satisfies: REQ-1.1, REQ-1.2    # or - (wiring/config only)
- Evidence: EV-code-001          # optional
- Held-as: `Arc<dyn TodoStore>`   # optional; how other components hold this one
- Implements: `axum::handler::Handler`  # optional; external trait paths
- Purpose: <one sentence, no code tokens>
- Interfaces:
  ```rust
  pub fn create(&self, input: CreateTodo) -> Result<Todo, TodoError>;
  ```

## Types
### MOD-1: <TypeName>
- Owner: DES-1
- Definition:
  ```rust
  pub enum TodoError { EmptyTitle, TitleTooLong { max: usize } }
  ```
- Raises:
  - EmptyTitle: `DES-3:create`, `DES-2:Title::parse` — title is empty after trimming

## APIs
### API-1: POST /todos
- Handler: `DES-4:create_todo`
- Auth: none | required
- Request: MOD-4               # or -
- Response: 201 MOD-5           # `200 MOD-5 (array)` for a list, `200 -` for no body
- Errors:
  - 400: `MOD-2:TodoError::EmptyTitle`
  - 422: DEP-1                  # a rejection produced by a library, described in that DEP's Contract

## Test Support
### TST-1: <Name>
- Kind: harness | fixture | double
- Phase: 1
- Files: crates/app/tests/support/mod.rs
- Depends: DES-5                 # or -
- Implements: `DES-2:TodoStore`   # doubles only: a trait declared in some DES Interfaces
- Interfaces:
  ```rust
  pub async fn spawn(port: u16) -> TestServer;
  ```

## Dependencies
### DEP-1: <crate>
- Version: 0.8
- Features: json, macros         # optional
- Scope: prod | dev
- Purpose: <prose>
- Contract:                      # optional; runtime semantics the design relies on
  - <statement> (EV-lib-001)

## Tools
### TOOL-1: cargo
- Min: 1.93
- Check: cargo --version
- Install: rustup update
- Required: yes | recommended

## Decisions
### KD-1: <title>
- Decision: <prose>
- Rationale: <prose>
- ADR: yes | no

## Excluded Tests
- E2E-3: <reason> — <alternative verification>
```

Rules:

- **Signatures live only in `Interfaces` and `Definition`.** Purpose, Decisions and Overview carry no code tokens (L05).
- **Code fields are real code with bodies elided.**
  - Functions end in `;` instead of a body. Trait definitions, impl blocks, `use` lines and attributes are written as in real source.
  - sigcheck turns each elided body into `todo!()` (C#: `throw new NotImplementedException()`) and compiles the result.
- **Required fields** (L16):
  - Every DES has Kind, Layer, Phase, Files, Depends, Satisfies and Purpose.
  - `Interfaces` is required for Kind logic, types, adapter and ui. It is optional for wiring and absent for config.
  - `Layer: -` is allowed only for config.
- **Kind** decides what must test a component (L11):

  | Kind | Must be tested by |
  |---|---|
  | logic, types | UT |
  | adapter | IT on every API whose Handler it owns (entry adapters: HTTP handlers, MCP tools) |
  | ui | CT |
  | wiring, config | Build and smoke |
- Every type named in an `Interfaces` block is defined in some `MOD-N` `Definition`, or comes from a `DEP` crate or the language prelude. This is checked by sigcheck, not by lint.
- **Completeness** (lint):
  - A DES with `Held-as` is constructed by someone else, so its Interfaces must declare a constructor (`fn new`, or a C# constructor) (L24).
  - An error enum is a MOD with a `Raises` field. Each of its variants has at least one `Raises` entry, and each entry names a `DES:fn` whose declared return type contains that enum (L25). A variant nobody raises is a design gap, not an implementation detail.
- **API Request / Response** refer to a DTO `MOD-N` whose Definition lists every field. Response keys are exactly those fields.
- A file belongs to exactly one DES or TST, except files listed under tech.md `Wiring Files` (L09). A file's path must match its Layer's `Paths` glob (L09).
- `Depends` follows the Layers table (L10), has no cycles (L19), and never points to a later Phase (L20).
- **Greenfield**: P0 contains at least one `Kind: config` DES that creates the workspace, toolchain pin and CI (L26).

### 4.4 test-design.md

```markdown
## Unit Tests
### DES-3
#### UT-3.1: <title>
- Target: `DES-3:create`
- Verifies: REQ-1.1
- Category: Happy | Boundary | Error | Edge | Negative
- Given:
  - input = `MOD-4:CreateTodo` { title: "buy milk" }
- Then:
  - returns `Ok` with a `MOD-1:Todo` whose title is "buy milk"
- Regression: BUG-12           # optional

## Component Tests
### DES-6
#### CT-6.1: <title>
- Target: DES-6
- Verifies: REQ-2.1
- Mount: <prose with qualified symbols>
- Action: <prose>
- Then:
  - <observable DOM / signal state>

## Integration Tests
### IT-1: <title>
- Target: API-1
- Verifies: REQ-1.1
- File: crates/app/tests/it_todos.rs
- Uses: TST-1
- Setup:
  - `TST-1:spawn` port = 0
- Request: POST /todos {"title": "buy milk"}
- Then:
  - status 201
  - body is `MOD-5:TodoResponse` with title "buy milk"

## System Tests
### ST-1: <title>
- Target: REQ-1
- Verifies: REQ-1.1, REQ-2.1
- File: ...
- Uses: TST-1
- Setup: (as IT)
- Steps:
  - <action>
- Then:
  - <observable>

## E2E Tests
### E2E-1: <title>
- Target: JRN-1
- File: ...
- Uses: TST-1
- Steps: ...
- Then: ...
```

Fields per block (L16):

| Block | Required | Optional |
|---|---|---|
| UT | Target, Verifies, Category, Then | State (preconditions in prose), Given (required when the Target takes parameters), Regression |
| CT | Target, Verifies, Mount, Action, Then | State, Regression |
| IT | Target, Verifies, File, Uses, Request, Then | Setup, State, Regression |
| ST | Target, Verifies, File, Uses, Steps, Then | Setup, State, Regression |
| E2E | Target, File, Uses, Steps, Then | Setup, State |

Rules:

- `UT-N.M` sits under `### DES-N`, and its Target is a function of DES-N (L12).
- **Target binding**:
  - `Given` binds the Target function's parameters by name, `name = value`. The set of names equals the parameter set of the signature, excluding `self` (L21).
  - `Setup` calls to `TST` functions bind that function's parameters the same way (L21).
- **Type binding**: a `MOD-N` type named in `Then` must appear in the Target function's return type or error type. For IT, it must appear in the API `Response` / `Errors` (L08).
- **Doubles**: a test may replace only a trait declared in some DES Interfaces, through a `TST` with `Kind: double` and `Implements:`. Mocking a concrete type, or introducing a seam design does not declare, is L22.
- **Single outcome**: `Then` contains no disjunction ("or", "または", "いずれか", "either") (L13) and no placeholders `[...]`, `TBD`, `TODO` (L14).
- **Layer boundary** (L12):

  | Layer | May target |
  |---|---|
  | UT | a `DES:fn` of Kind logic or types |
  | CT | a DES of Kind ui |
  | IT | an `API` |
  | ST | a `REQ` whose ACs span ui and api |
  | E2E | a `JRN` |

- Coverage (L11):
  - every AC has at least one test
  - every DES is tested as its Kind requires (§4.3)
  - every API status in `Responses` / `Errors` has an IT
  - every `Raises` entry (variant × function) is covered: by a UT whose Target is that function and whose Then names the variant, or, when the function is an adapter handler, by an IT on that handler's API whose Then names the variant
  - every JRN has an E2E
  - every DEP `Contract` statement has an IT
- Test files for UT and CT come from tech.md `Test Layout`; IT / ST / E2E declare `File`.

## 5. Generated documents

`tasks.md` and `trace.md` start with `<!-- GENERATED by spec-plan.sh: do not edit -->`. Editing them by hand is blocked (guard-edit) and detected (`spec-plan.sh --check`).

## 6. Fixed dependency order

```
steering ──► request-spec ──► requirements ──► design ──► test-design
                                   └──────────────────────────► test-design
```

An approved document becomes `stale` when any upstream document is re-approved with different content (see `contract/approval-ledger-v1.md`).

## 7. Lint codes

| Code | Name | Scope |
|---|---|---|
| L01 | DUP_ID | ID defined twice |
| L02 | UNRESOLVED_REF | reference to an undefined ID |
| L03 | LINE_REF | line-number reference |
| L04 | UNQUALIFIED_CODE | code token outside design |
| L05 | CODE_OUTSIDE_OWNER | code token in design prose |
| L06 | SYMBOL_NAME_MISMATCH | `ID:Name` where Name is not declared by ID |
| L07 | UNKNOWN_MEMBER | `ID:Name::Member` where Member is not in Name |
| L08 | TYPE_NOT_IN_TARGET_SIGNATURE | expected type absent from Target return / error / API response |
| L09 | FILE_OWNERSHIP | file owned twice or outside its Layer paths |
| L10 | LAYER_DEP | Depends violates the Layers table |
| L11 | COVERAGE | missing mapping (§4.2, §4.4) |
| L12 | LAYER_BOUNDARY | test Target outside its layer |
| L13 | DISJUNCTION | alternatives in Then |
| L14 | PLACEHOLDER | unfilled template text |
| L15 | FORBIDDEN_SECTION | section not allowed in this document |
| L16 | UNKNOWN_FIELD | field not allowed in this block, or required field missing |
| L17 | EXCLUDED_ENV | Excluded Tests entry without reason or alternative |
| L18 | EV_MISSING | referenced EV file absent, or required category uncited |
| L19 | CYCLE | Depends cycle |
| L20 | PHASE_ORDER | dependency on a later Phase |
| L21 | PARAM_BINDING | Given / Setup names differ from the signature parameters |
| L22 | UNDECLARED_DOUBLE | double of a concrete type or an undeclared seam |
| L23 | TECH_SECTION | tech.md section missing |
| L24 | MISSING_CONSTRUCTOR | held DES without a constructor in Interfaces |
| L25 | RAISES_MISMATCH | error variant without Raises, or Raises names a fn that does not return the enum |
| L26 | GREENFIELD_BOOTSTRAP | greenfield design without a P0 config DES |
