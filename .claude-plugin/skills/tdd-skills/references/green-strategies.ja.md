# Green 戦略

失敗テストをできるだけ早くパスさせるための3つの戦略。

## 1. Fake It

**最も安全なアプローチ。まず定数を返してテストをパスさせる。**

```
// テスト: 空コレクションの合計はゼロ
// 実装: return 0  (ハードコードされた定数)
```

使用場面:
- 実装パスが不明確
- 複雑なロジックが必要
- 小さなステップで信頼を築く

## 2. Triangulation

**複数のテストケースから一般化する。**

プロセス:
1. 最初のテスト → Fake It（定数を返す）
2. 定数を壊す2番目のテストを追加
3. 両方のテストをパスするよう一般化
4. 必要に応じてさらにテストを追加

```
テスト1: 空 → 合計は 0       →  return 0
テスト2: 1アイテム(100) → 合計 100  →  return sum(items)
```

使用場面:
- 一般化の方法が不明確
- テストに設計を駆動させたい
- 早すぎる抽象化を避けたい

## 3. Obvious Implementation

**最速だがリスク最大。実際のソリューションを直接実装する。**

使用場面:
- ソリューションが自明に明確
- シンプルなロジック
- 問題ドメインに経験がある

**「自明な」実装後にテストが失敗したら、即座に Fake It にフォールバックする。**

## 判断フロー

```
実装は自明か？
  ├─ はい → Obvious Implementation を試す
  │         ├─ パス → 完了
  │         └─ 失敗 → Fake It にフォールバック
  └─ いいえ → Fake It から始める
              ├─ テスト1つ → fake を維持
              └─ 複数テスト → Triangulate で一般化
```

## まとめ

| 戦略 | 速度 | 安全性 | 使用場面 |
|-----|------|-------|---------|
| Fake It | 遅い | 高い | デフォルト選択、不確実な場合 |
| Triangulation | 中程度 | 高い | 複雑な一般化 |
| Obvious Implementation | 速い | 低い | 自明に明確な場合のみ |

**迷ったら Fake It。経験があれば Obvious。複雑なら Triangulate。**
