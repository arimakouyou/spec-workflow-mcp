# TDD と設計

## TDD は設計手法でもある

TDD を実践すると自然に以下が導かれる:

1. **YAGNI**: テストが要求するものだけを実装する
2. **単一責任**: テスト可能なクラスは明確な責務を持つ
3. **依存関係逆転**: テストダブルがインターフェースベースの設計を促進する
4. **疎結合**: テスト可能なコードは結合度が低い

## テスト可能 vs テスト不可能な設計

**テスト不可能** — 外部システム（DB 接続、HTTP クライアント、ファイルシステム、クロック）への直接依存がクラス内部で作成される。

**テスト可能** — 依存関係がコンストラクタ/メソッドパラメータを通じて注入され、テストダブルに置換可能。

## TDD がもたらす設計の利点

### 1. 明確なインターフェース
テストを先に書くことで、呼び出し側の視点から使いやすい API を設計せざるを得ない。

### 2. 責務の分離
テストが複雑になったら、テスト対象クラスの責務が多すぎる。分割する。

### 3. 疎結合
テストダブルの使用がインターフェース/プロトコルを通じてコンポーネントを自然に疎結合にする。

## テスト容易性の原則

### 外部依存を注入する
内部で依存関係を作成しない。コンストラクタやパラメータ経由で受け取る。

### 副作用とロジックを分離する
純粋な計算を1つの関数、I/O を別の関数に。純粋な部分を直接テストする。

### 動作を決定的にする
非決定性の源（時刻、乱数、UUID）を注入して、テストが制御できるようにする。

## TDD から生まれる設計パターン

- **Strategy**: 注入された動作 → 異なる戦略で自然にテスト可能
- **Repository**: 抽象化されたデータアクセス → 実 DB をインメモリ Fake に置換
- **Factory**: 複雑なオブジェクト生成 → 分離してテスト可能

> 「良いテストを書くことは自然に良い設計に繋がる。」— t-wada

**TDD = Design-Driven Development**
