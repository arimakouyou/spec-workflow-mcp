# TDD 実践テクニックとアンチパターン

## 不確実な仕様への対処

仕様が曖昧な場合、抽象的なテストではなく具体的な例から始める。最も単純で具体的なケースのテストを書き、そこから拡張する。

**悪い例**: `test_calculate_price`（抽象的すぎ、何をアサートするか不明確）
**良い例**: `test_calculate_price_single_item_no_discount`（具体的、アクション可能）

## レガシーコードへの TDD 適用

1. 現在の動作をキャプチャするキャラクタリゼーションテストを書く
2. テストの保護下で小さなステップでリファクタリング
3. TDD を使って新機能を追加

キャラクタリゼーションテストは「正しい」動作ではなく「現在の」動作をアサートし、リファクタリングのセーフティネットを作る。

## テストが複雑になった場合

複雑なテストは複雑なコードのサインである。以下で対応:
1. テストヘルパーメソッドの抽出
2. テストデータの Builder / Factory パターンの使用
3. テスト対象クラスの分割（単一責任の原則）

## アンチパターン

### 1. テストをスキップする
テストを先に書くこと。常に。

### 2. ステップが大きすぎる
テストが複数のことを一度に実装する必要がある場合、より小さなテストに分割する。

### 3. 自明な getter/setter のテスト
データアクセスではなく動作をテストする。getter がフィールドを返すだけなら、専用のテストは不要。

### 4. プライベートメソッドの直接テスト
公開 API を通じてテストする。プライベートメソッドが専用テストを必要とするほど複雑なら、別のクラスに分離すべき。

### 5. テスト間の相互依存
各テストは独立して動作しなければならない。テスト間で共有される可変状態は不可。

## TODO リストテクニック

書くべきテストケースのリストを管理する。進めながらチェックし、実装中に浮かんだ新しいアイデアを追加する。

利点:
- 現在のテストに集中できる
- アイデアを失わない
- 進捗が可視化される
