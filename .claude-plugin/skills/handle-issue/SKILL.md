# Issue ハンドリング — GitHub Issue ワークフロー

GitHub Issue を取得・分析し、変更規模に基づいて最適なワークフローに自動ルーティングする。

## 入力

- **issue**: Issue 番号（例: `#42`, `42`）または Issue URL。`$ARGS` の最初の引数として受け取る。

**呼び出し形式**: `/handle-issue <issue-number>` （例: `/handle-issue 42`）

引数が未指定の場合はユーザーに Issue 番号を確認する。

## 前提条件チェック（MANDATORY）

以下のチェックを順番に実行する。いずれかが失敗した場合は **STOP** し、対処方法を案内する。

### 1. gh CLI 認証確認

```bash
gh auth status
```

失敗時: 「`gh auth login` を実行して GitHub CLI を認証してください」と案内して STOP。

### 2. リポジトリ確認

```bash
gh repo view --json nameWithOwner -q '.nameWithOwner'
```

失敗時: 「GitHub リポジトリのルートディレクトリで実行してください」と案内して STOP。

### 3. ワーキングツリー確認

```bash
git status --porcelain
```

未コミットの変更がある場合: **STOP**。`git commit` または `git stash` でワーキングツリーをクリーンな状態にしてから再実行するよう案内する。4B パスでは最終的に `/create-pr` を実行し、その前提としてクリーンなワーキングツリーが必須。

## 手順

### 1. Issue 情報の取得

```bash
gh issue view {number} --json title,body,labels,assignees,milestone,comments,state
```

**状態チェック**:
- Issue が `CLOSED` の場合 → 警告を表示し、続行するか確認
- Issue に自分以外の assignee がいる場合 → 警告を表示し、続行するか確認

**関連 Issue/PR の検出**:
- Issue 本文から `#N`、`closes #N`、`fixes #N`、`related to #N` 形式のクロスリファレンスを抽出
- 検出された関連 Issue/PR をユーザーに参考情報として提示（ブロッキングではない）

### 2. コードベース分析

Issue の内容を基に、影響範囲を調査する:

1. **関連ファイルの特定**: Issue に記載されたキーワード、エラーメッセージ、関数名を Grep/Glob で検索
2. **影響範囲の推定**: 関連ファイル数、変更が必要なモジュール/コンポーネント数を推定
3. **テストカバレッジの確認**: 関連コードに既存テストがあるか確認
4. **アーキテクチャ影響の判定**: 新規 API、DB スキーマ変更、新コンポーネント追加が必要かを判断

### 3. 変更規模の分類（トリアージ）

以下のスコアリングマトリクスで変更規模を数値化する。

| 基準 | 重み | 大規模 (3点) | 中規模 (2点) | 小規模 (1点) |
|------|------|-------------|-------------|-------------|
| 影響ファイル数 | x3 | 6ファイル以上 | 3〜5ファイル | 1〜2ファイル |
| アーキテクチャ変更 | x3 | 新API/DB変更/新コンポーネント | 既存APIの拡張 | 既存コード内の修正 |
| ラベル | x2 | feature / enhancement | bug（複雑） | bug（単純） |
| 要件の明確さ | x2 | 曖昧・要議論 | 概ね明確 | 再現手順が明確 |
| テストカバレッジ | x1 | カバレッジなし | 部分的カバー | 既存テストあり |

**合計スコア範囲**: 11点（最小）〜 33点（最大）

**ルーティング判定**:
- **27点以上** → **4A. 大規模変更パス**（Spec Workflow）
- **18〜26点** → **4C. 判断が必要パス**（ユーザー確認）
- **17点以下** → **4B. 軽微なバグ修正パス**（TDD 直接対応）

スコアリング結果は以下のフォーマットで必ず表示する:

```
## トリアージ結果: Issue #{number}

| 基準 | スコア | 重み | 小計 | 根拠 |
|------|--------|------|------|------|
| 影響ファイル数 | {1-3} | x3 | {小計} | {理由} |
| アーキテクチャ変更 | {1-3} | x3 | {小計} | {理由} |
| ラベル | {1-3} | x2 | {小計} | {理由} |
| 要件の明確さ | {1-3} | x2 | {小計} | {理由} |
| テストカバレッジ | {1-3} | x1 | {小計} | {理由} |

**合計**: {total}/33 → **{パス名}**
```

### 4A. 大規模変更パス — Spec Workflow へルーティング

大規模な変更は仕様書を先に作成することで、手戻りを防ぐ。

1. **ブランチ作成の確認**: ユーザーにブランチ名 `feat/issue-{N}-{slug}` を提案し確認を取る
   - `{slug}` は Issue タイトルから kebab-case で生成（最大30文字）
   - 例: `feat/issue-42-add-user-export`

2. **ブランチ作成**:
   ```bash
   git checkout -b {branch-name}
   ```

3. **Issue コンテキストの整理**: 以下の情報をまとめる
   - Issue タイトルと本文
   - ラベルとマイルストーン
   - コードベース分析の結果（影響ファイル、アーキテクチャ影響）
   - 関連 Issue/PR

4. **Spec Workflow への遷移**:
   - spec-name を Issue タイトルから kebab-case で自動生成
   - `/spec-request-spec` スキルをロードして即座に開始
   - Issue URL を request-spec.md の「背景」セクションに記録する
   - Issue 本文をユースケースの初期入力として渡す

   > `/spec-request-spec` スキルをロードし、即座に開始する。上記の Issue コンテキストをリクエスト仕様の入力として使用する。

### 4B. 軽微なバグ修正パス — TDD 直接対応

明確で小規模なバグは、仕様書なしで TDD アプローチで直接修正する。

1. **ブランチ作成の確認**: ユーザーにブランチ名 `fix/issue-{N}-{slug}` を提案し確認を取る
   - 例: `fix/issue-15-null-pointer-in-parser`

2. **ブランチ作成**:
   ```bash
   git checkout -b {branch-name}
   ```

3. **RED — 再現テスト作成**:
   - Issue の再現手順を基にテストを作成
   - テストが **失敗** することを確認（バグの再現）
   - `/tdd-skills`（または Rust プロジェクトの場合 `/tdd-skills-rust`）を参照

4. **GREEN — 最小限の修正実装**:
   - テストが **成功** する最小限の修正を実装
   - 既存テストが壊れていないことを確認

5. **REFACTOR — コード整理**:
   - 修正コードの品質を改善（重複排除、命名改善など）
   - テストが引き続き成功することを確認

6. **品質チェック**:
   - プロジェクトの `quality-checks.md` ルールに従った品質チェックを実行
   - 失敗した場合は修正を試行（最大3回）、解決できなければユーザーに報告

7. **PR 作成**:
   `/create-pr` スキルに以下の引数を渡して PR を作成する:
   - `--title "{Issue タイトルに基づく修正の要約}"`
   - `--closes {number}`

   > 上記の引数で `/create-pr` スキルをロードする。スキルは IT/E2E テストを実行し、UI 変更を検出し、該当する場合はスクリーンショットを取得して、構造化されたテスト結果を含む PR を作成する。

### 4C. 判断が必要パス — ユーザー確認

スコアが中間帯の場合、ユーザーの判断を仰ぐ。

1. **分析結果の提示**:
   - トリアージ結果のスコアテーブル（手順3のフォーマット）
   - コードベース分析の要約（影響範囲、リスク）
   - 推奨パスとその理由

2. **選択肢の提示**:
   ```
   以下のいずれかを選択してください:
   A) 大規模変更として Spec Workflow で対応（仕様書を作成してから実装）
   B) 軽微な修正として TDD で直接対応
   C) 追加調査が必要（より詳しくコードベースを分析する）
   ```

3. **ユーザーの決定を待機**: 選択に応じて 4A または 4B のパスに進む。C の場合は追加分析を実施して再度トリアージする。

## ブランチ命名規則

| Issue タイプ | ブランチプレフィックス | 例 |
|-------------|---------------------|-----|
| bug | `fix/issue-{N}-{slug}` | `fix/issue-15-null-pointer-in-parser` |
| feature / enhancement | `feat/issue-{N}-{slug}` | `feat/issue-42-add-user-export` |
| その他 | `fix/issue-{N}-{slug}` | `fix/issue-99-update-error-message` |

`{slug}` は Issue タイトルを kebab-case に変換し、最大30文字に切り詰める。

## ルール

- ブランチ作成前に必ずユーザー確認を取る
- Issue が `CLOSED` の場合は警告し、ユーザーの明示的な続行指示がなければ STOP
- 他人にアサインされた Issue は警告し、ユーザーの明示的な続行指示がなければ STOP
- Spec Workflow（4A パス）への遷移時、Issue URL を request-spec.md に必ず記録する
- TDD 直接対応（4B パス）では、品質チェックが全て PASS してから PR を作成する
- スコアリング結果は必ずテーブル形式で表示し、判断根拠を透明にする
- 関連 Issue/PR は参考情報として提示するが、ブロッキング要件としない
